# SOURCE INGESTION / DATA COLLECTION v1.0 (черновик)

**Репозиторий:** Yumis84/ortomediya  
**Связан с:** DATA_MODEL, IDENTITY_RESOLUTION, REVIEW_LIFECYCLE  
**Статус:** проектирование (требует утверждения)  
**Дата:** 2026-08-24

Как получать отзывы из разных источников, нормализовать их и помещать в единый список компании, не смешивая сущности.

---

## 1. Цель

Собрать отзывы из внешних источников → нормализовать → привязать к правильному Company Profile через Identity Resolution → сохранить как Review (FACT) с полным Provenance → обновить Analysis и AI Summary.

Не смешивать сущности.  
Не создавать отдельные списки «отзывы Яндекса / 2ГИС / Google».

---

## 2. Высокоуровневый поток

```
1. Source Discovery / Targeting
   (какая карточка/страница относится к нашей Entity)

2. Collection
   (получение сырых данных допустимым способом)

3. Normalization
   (единый формат Review + Provenance)

4. Identity Resolution
   (привязка к otzovik_id / branch_id)

5. Deduplication
   (не создавать дубли одного и того же отзыва)

6. Status Assignment
   (source_status = active и т.д.)

7. Persist FACT

8. Trigger Analysis + AI Summary recalculation
   (при значимом изменении source_data_version)
```

---

## 3. Принципы сбора

- Только допустимые методы (public pages, официальные API, если есть, ручной ввод на первом этапе).
- Фиксировать `collection_method` в provenance.
- Не выдумывать данные.
- Сохранять `source_url` только если он реален; иначе `source_url_note`.
- Соблюдать rate limits и условия использования источников (юридический трек отдельно).

---

## 4. Нормализация в Review

Каждый сырой отзыв → один объект Review:

- `source.type` / `source.name` / `source_id`
- `source_review_id` (если есть)
- `source_url` + `source_url_note`
- `rating`, `review_text`, `published_at`
- `collected_at`, `content_hash`
- `provenance` (полный)
- `source_status` = active (по умолчанию при успешном сборе)
- `moderation_status` = active (сборщик **не** ставит disputed/hidden)

---

## 5. Привязка к компании

Только через Identity Resolution:

```
SOURCE ENTITY (карточка в Яндекс/2ГИС/…)
  ↓
IDENTITY RESOLUTION
  ↓
otzovik_id (+ optional branch_id)
  ↓
Review.company_id
```

Если identity не установлена с достаточной уверенностью — отзыв **не** попадает в профиль автоматически (или попадает в очередь на проверку).

---

## 6. Дедупликация

Один и тот же отзыв не должен появляться дважды.

Ключи дедупликации (внутренние):
- `source` + `source_review_id`
- или `content_hash` + `source` + приблизительная дата (если нет source_review_id)

При повторном сборе — обновление existing Review (статусы, текст если изменился), а не новый объект.

---

## 7. Обновление и удаление в источнике

При следующем проходе:
- отзыв найден → source_status остаётся/становится active;
- отзыв исчез → source_status = removed_from_source (сборщик имеет право менять только Source Status);
- текст изменился → фиксируем was_modified + новый snapshot (если политика позволяет).

---

## 8. Триггеры пересчёта

Любое значимое изменение набора отзывов → новая `source_data_version` → Analysis и AI Summary помечаются stale и пересчитываются.

---

## 9. Первый этап (ручной / полуручной)

На старте допускается:
- ручной сбор и загрузка;
- полуавтоматический импорт;
- без полноценных парсеров в продакшене.

Архитектура должна позволять позже заменить ручной шаг на автоматизированный collector без смены модели Review.

---

## 10. Юридические и репутационные риски (напоминание)

- Условия использования источников
- Авторские права / право на цитирование
- Персональные данные авторов
- Возможность удаления по требованию

Отдельный трек: Data Retention + Legal Policy.
