## 1. Принцип безопасности

При сомнении — **НЕ объединять**.

Лучше показать «Возможна связь с другой организацией. Проверка продолжается», чем смешать отзывы двух разных компаний.

---

## 2. ENTITY vs COMPANY PROFILE

- **ENTITY** — реальная идентифицируемая сущность.
- **COMPANY PROFILE** — публичный профиль Отзовика.

Юридическое лицо и бренд не обязательно одно и то же.

Структура:
```
Бренд «Ортомедия»
  ↓
юридическое лицо ООО «Ортомедия»
  ↓
филиалы / точки
  ↓
карточки в источниках
```

---

## 3. Идентификаторы

| Уровень | Поле | Публичность |
|---------|------|-------------|
| Канонический | `otzovik_id` (ULID) | да |
| Человекочитаемый | `slug` | да |
| Алиасы | `aliases[]` (только полезные для понимания) | да |
| Юридические | `legal_name`, `inn`, `ogrn` | условно (см. ниже) |
| Внешние | `external_ids` (упрощённо) | частично |

---

## 4. Confidence и автоматическое связывание

Один внешний ID **не** является доказательством идентичности.

Автоматическое связывание только при достаточном наборе совпадений:
- название
- адрес
- телефон
- официальный сайт
- география
- дополнительные признаки

Политика:
- **HIGH** → автоматическое связывание допустимо
- **MEDIUM** → только полуавтоматическая проверка
- **LOW** → не связывать автоматически

Критические расхождения (другой адрес + другой телефон и т.п.) **блокируют** автоматическое объединение независимо от score.

---

## 5. Aliases

- Существуют во внутренней модели.
- Публично — только варианты, помогающие AI понять идентичность.
- Не публиковать технические/поисковые промежуточные варианты.
- `alias ≠ отдельная компания`.

---

## 6. INN / OGRN

Публикация допускается только если:
- получены из допустимого источника;
- относятся именно к данной юридической сущности;
- публикация допустима по правилам и политике проекта.

Не являются обязательным публичным идентификатором профиля.  
Не перегружают человеческий UI.  
В machine-readable могут быть полезны при достоверном происхождении.

---

## 7. Merge — полуавтоматический

Автоматически:
- обнаруживаем кандидатов;
- формируем `merge_candidate`, confidence, matching_signals, conflicts.

Окончательное объединение — **после проверки**.

Не объединять автоматически только по:
- одинаковому названию;
- одинаковому телефону;
- похожему адресу;
- совпадению домена без других подтверждений.

Ошибочное объединение хуже двух временно не связанных профилей.

---

## 8. Unmerge (обязательно)

При обнаружении ошибочного объединения:
- событие `unmerge`;
- история сохраняется;
- отзывы возвращаются к правильным сущностям;
- Analysis и AI Summary пересчитываются;
- provenance сохраняется.

Ничего не исчезает из audit trail.

---

## 9. Публичные сигналы ambiguity

При неоднозначности:
- `identity_status`: `needs_review` (или аналогичный флаг)
- `conflicts` с type `possible_duplicate` / `address_mismatch` и т.д.
- AI должен понимать, что идентичность не установлена окончательно.

Не объединять данные молча.

---

## 10. Цепочка для отзывов

```
SOURCE REVIEW
  ↓
SOURCE ENTITY
  ↓
IDENTITY RESOLUTION
  ↓
COMPANY PROFILE
  ↓
REVIEW
```

Отзыв нельзя переносить только из-за совпадения названия.

При изменении identity resolution:
- Review → reassignment
- Analysis recalculation
- AI Summary recalculation

---

## 11. /entity/{id}.json

На первом етапе **не** делаем.

Основной объект для человека и AI — `/profile.json`.  
Entity resolution остаётся внутренним слоем.

---

## 12. Утверждённые решения (Yumis, 2026-08-24)

1. Автоматическое связывание только при достаточном наборе сигналов; критические расхождения блокируют.
2. Aliases — публично только полезные варианты.
3. INN/OGRN — условная публикация, не обязательный идентификатор.
4. Merge — полуавтоматический.
5. Unmerge обязателен, история сохраняется.
6. ENTITY ≠ COMPANY PROFILE.
7. Отдельный `/entity/{id}.json` в v1 не делаем.
8. При сомнении — не объединять; показывать needs_review / conflicts.
9. Отзыв не переносится только по названию.

## 13. YUMIS APPROVAL — уточнения и финальная фиксация

### 13.1 Confidence для автоматического принятия external_id

Не использовать один универсальный confidence score как единственное основание.

Автоматическое связывание допускается только при достаточном наборе совпадений: название, адрес, телефон, официальный сайт, география и дополнительные признаки.

Политика:
- **HIGH** → автоматическое связывание допустимо.
- **MEDIUM** → только полуавтоматическая проверка.
- **LOW** → не связывать автоматически.

Критические расхождения, например другой адрес + другой телефон, блокируют автоматическое объединение независимо от итогового score.

### 13.2 Aliases

Aliases существуют во внутренней модели. Публично показываются только варианты названия, которые помогают AI понять идентичность компании. Технические ключи, поисковые варианты и промежуточные результаты identity resolution не публикуются.

`alias ≠ отдельная компания`.

### 13.3 INN / OGRN

Публичное отображение допускается только если данные получены из допустимого источника, относятся именно к данной юридической сущности и их публикация допустима применимыми правилами и политикой проекта.

INN/OGRN не являются обязательным публичным идентификатором. В обычном UI они не должны перегружать профиль. В machine-readable слое юридические идентификаторы допускаются при достоверном происхождении.

### 13.4 Merge

Выбран **полуавтоматический merge**.

Система автоматически обнаруживает кандидатов и формирует:
- `merge_candidate`
- `confidence`
- `matching_signals`
- `conflicts`

Окончательное объединение выполняется после проверки.

Особенно запрещено автоматически объединять компании только по одинаковому названию, одинаковому телефону, похожему адресу или совпадению домена без других подтверждений.

### 13.5 Unmerge

Обязательно предусмотреть обратное разделение. При ошибочном merge:
- создаётся событие `unmerge`;
- история сохраняется;
- отзывы возвращаются к правильным сущностям;
- Analysis пересчитывается;
- AI Summary пересчитывается;
- provenance сохраняется.

Ничего не удаляется из audit trail.

### 13.6 ENTITY и COMPANY PROFILE

Понятия разделены:

**ENTITY** → реальная идентифицируемая сущность.

**COMPANY PROFILE** → публичный профиль Отзовика, который может представлять одну или несколько связанных сущностей только при наличии достаточных оснований.

Юридическое лицо и бренд не обязательно являются одним объектом.

### 13.7 Публичный endpoint ENTITY

В v1 отдельный `/entity/{id}.json` **не создаётся**.

Основной объект для пользователя и AI — `/profile.json`. Entity resolution остаётся внутренним слоем.

### 13.8 Identity conflicts

Если обнаружены одинаковое название у разных компаний, разные адреса, разные телефоны, разные юридические лица, возможные дубли или неоднозначная принадлежность филиала — данные не объединяются молча.

Профиль получает соответствующий статус, например:
- `identity_confidence: "medium"`
- `identity_status: "needs_review"`

AI обязан понимать, что идентичность не установлена окончательно.

### 13.9 Правило для отзывов

Отзыв нельзя переносить в профиль другой компании только потому, что совпало название.

Каноническая цепочка:

```
SOURCE REVIEW
↓
SOURCE ENTITY
↓
IDENTITY RESOLUTION
↓
COMPANY PROFILE
↓
REVIEW
```

Если identity resolution изменилось:

`Review → reassignment → Analysis recalculation → AI Summary recalculation`.

### 13.10 Принцип безопасности

При сомнении — **НЕ объединять**.

Предпочтительный результат:

> «Возможна связь с другой организацией. Проверка продолжается»

Это безопаснее, чем создать единый профиль с отзывами двух разных компаний.
